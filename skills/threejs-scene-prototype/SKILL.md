# three.js 场景原型：搭建、迭代、自检、交接

这份技能来自一个带角色的 3D 场景网页原型从第 1 版迭代到 v1.0.0 的全过程。目标是：做出一个能转镜头、能互动的 3D 场景网页原型，按设计师的口头反馈快速迭代，每一轮都用图说话，最后能干净地交给研发。

## 0. 开工前先确认的事

- 画布尺寸和载体（例如 iOS 390×844 的手机样机）。
- 角色（IP）是否已有模型或代码；有的话原件不动，只做副本。
- 设计系统的硬规则（颜色 token、强调色用几次、深色不能死黑等）。
- 产出发到哪里：私有网页（Artifact）、项目文档、压缩包。默认不公开。
- 说清楚这是**原型参考实现**，不是可上线的工程；数据和对话是示例。

## 1. 工程结构（从第一天就分开）

```
src/ip/        角色：模型、材质、表情、动作、穿着道具
src/scene/     场景：天空、云、地形、草、雪、道具、天气粒子、后期
src/behavior/  行为：镜头、走路、互动、状态机、对外接口
src/host/      宿主：画布和每帧循环（原生 three 或 react-three-fiber）
src/demo-ui/   演示界面和调试面板（不是交付内容）
assets/        导出的 GLB，ip 和 scene 分开
tools/         构建、本地预览、截图脚本
docs/          交接说明、结构与接口、版本记录
```

- 界面和 3D 之间只留一个对外接口对象（例如 `window.XxxWorld`：`pet()`、`walkTo()`、`setState()`、`state`、`info`）。
- 所有自定义着色器共用一组 uniform（昼夜、雨、雪、时间、角色位置、灯的位置），改一处全场景生效。
- 如果早期图快把代码写在一个作用域里，交接时要**如实写明**“分开放了但没有解耦”，并列出交叉点和重构顺序。

## 2. 每一轮迭代的固定动作

1. **先备份再改**：上一版的源码和构建结果另存一份带版本号的副本，永不覆盖原件。
2. 改代码 → 构建 → **无头浏览器截图** → 自己先看图 → 不对就再改，对了才发。
3. 发给用户的是**前后对比图**（上一版 / 这一版并排，中文标注），不是长文字。
4. 回复用中文、结论先行；逐条对应用户说的话；单独列出**没验证的**和**自己拿主意的**（颜色、数值、默认值）。
5. 更新已发布的同一个网页（保持链接不变），并在项目文档里追加这一版的小节：反馈原话要点、改了什么（表格）、没做什么、备份在哪。
6. 用户的两句话互相矛盾时（例如先说不要某个部件，后来又选了带这个部件的截图），按最新的做，同时做一个开关让对方二选一，并明确指出矛盾。
7. 用户发参考图时，只对齐质感，不照搬画面，也在回复里说明。

## 3. 无头截图自检的做法和坑

- 用 Playwright + Chromium，启动参数 `--use-gl=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`；给人看的图用 2 倍像素比，自己看的用 1 倍。
- 给页面加测试用的网址参数：`fast`（跳过进场动画、状态直接到位）、`skip=N`（每 N 帧渲染一次）、时间流速（慢放）、固定姿态。
- **软件渲染很慢**（每帧可能几秒），模拟时间远慢于真实时间。截图前先渲染两三帧再冻结画面，否则截图会超时。
- 要看动作（跳跃、弯曲）就把时间流速调到 0.1 左右，连续截十几帧拼成一条。
- **功能有解锁条件时，测试参数要满足条件。**（曾经在功能未解锁的参数下去截某个天气，实际截到的是默认天气，还报告成“已检查”。发现后要主动更正。）
- 每次构建后看控制台有没有报错；每次改完至少回归：默认夜晚、白天、每种天气、一次互动。
- 无头环境只能证明“画面对、没报错”，**不能说明真机帧率和手感**，每次都要写明。可以用每帧耗时做版本间的相对比较，发现变慢就回查。
- 本地预览服务有运行时限，会被系统停掉；改成“渲染时临时启动、渲染完就关”。

## 4. 视觉上踩过的坑和可复用的做法

**总原则：先问清楚用户说的“硬”“不够软”“不像”指的是哪个东西，再动手。** 曾经把“画面有点硬”理解成天空的问题，其实对方说的是草地。

- **草地**：叠层（shell）画法便宜；要“软”就加长、根宽尖细、每根微弯、成片有长有短、随风摆（顶点偏移随高度平方增大）；角色身下把草压低。层数直接决定开销，每层里的计算能省则省（公共地面颜色函数里不要夹带只有个别情况才用的噪声）。
- **雪地**：不要只换颜色。加一层有厚度的雪面：起伏的雪堆、角色坐陷和鼓边、灯周围的浅坑、道具边的积雪；明暗用“受光面亮、背光面蓝紫”。
- **白天要像白天**：蓝天、白云、亮绿、浅蓝雾；界面上的深色遮罩在白天要减淡。
- **云**：一堆球直接叠会“一团糟”。用 three.js 自带的 `MarchingCubes`（`three/addons/objects`）把团块融合成一整张表面，底部把场截断得到平的云底；边缘不用透明，而是让靠近轮廓的地方融进天空色；颜色不要画在会旋转的贴图上。
- **道具颜色发淡**：标准材质会被场景灯光和色调映射冲淡；要“颜色准”就用不受光的平涂材质并关掉色调映射，要“有细节”就用受光材质并接受变浅。
- **辉光**：只让亮的东西向周围“溢光”，不要提亮物体本身，否则角色的五官会被洗掉。
- **后期与遮罩**：可以把画面的透明通道当遮罩（远近、是否接收辉光）；新加的着色器必须遵守同一约定。
- **两套颜色流程**：标准材质走色调映射，自定义着色器直接写显示颜色。接入要求统一色彩流程的后期库之前，先评估会不会让已确认的配色偏移。
- **点精灵**：近处要限制最大尺寸并淡出，否则贴近镜头时会铺满屏幕、极慢。
- **饱和度**：用户说“太灰”又选了较淡的图时，取中间值并把两张都放进对比图。

## 5. 关于库和工具的如实说明

- **react-three-fiber 不是另一个渲染器**，是同一个 three.js 上的 React 写法；装上它画面不变。它的价值是配套组件和工程组织。接入方式：fiber 提供 `{gl, scene, camera}` 和每帧循环，原有世界代码作为一个 `startWorld()` 模块在里面运行。
- three.js 的 npm 包自带 `examples/jsm` 下的附加模块（MarchingCubes、ImprovedNoise、Sky、Water、Lensflare、GLTFExporter、各种后期 Pass），需要时优先用它们，不要重复造。
- 代码生成的模型有上限；要更好的形状应在建模软件里做（如果用户电脑上的 Blender 可用，操作前先征得同意，并放进单独的集合）。

## 6. 交接打包

1. **冻结版本**：定版本号，记录“已定的决定”和“还没定的”。
2. **拆分并验证**：按第 1 节的目录拆文件，每个文件开头写归属和边界；验证拆分后的构建结果与发布版一致。
3. **导出 GLB**：用 `GLTFExporter` 在无头浏览器里导出角色、穿着、道具、场景物件；导出前把姿态归零、隐藏粒子和光晕、把自定义着色器换成替代材质；导出后**重新加载渲染一张模型一览图**确认可用。
4. **写三份文档**：README（怎么跑、目录）、交接说明（交付清单、哪些分开了哪些还耦合、模型文件里没有什么、关键参数、离上线还差什么、降低维护成本的建议和重构顺序、验收步骤）、结构与接口（职责表、共享状态、对外接口、网址参数、约定）。再加一份版本记录。
5. **干净目录验证**：把压缩包解到全新目录，重新安装依赖并构建，确认与包内构建结果一致，再发出。
6. UI 不进 3D 交付物；演示界面单独放并标明“仅演示”。
